# 记忆检索性能对比

本文记录 Qdrant、Redis 三级缓存和 MySQL 直读三条检索路径的受控微基准结果。

## 测试口径

- 日期：2026-09-23；环境为远端 WSL 上的单个后端进程、MySQL、Redis 与 Qdrant 容器。
- 使用同一条结构化问题查询，并在计时循环外只生成一次问题 Embedding。因此结果只表示**记忆检索耗时**，不包含 Embedding API、HTTP 调用方和 Agent 推理时间。
- 每组先预热 8 次，再串行记录 50 次；Redis 组读取的是预热后的三级缓存。
- `MEMORY_RETRIEVAL_MAX_CANDIDATES=500`，使 Redis 和无缓存路径完整读取并比较 300 条候选记忆。
- Qdrant 以相同作用域过滤向量索引，直接返回 `Top-K x candidateMultiplier` 的少量候选，再由 MySQL 校验命中记忆的版本和作用域。它不需要将 300 条向量传回 Java 逐个计算。

## 为什么区分作用域

生产检索会同时考虑当前仓库的专属记忆和全局通用记忆；两类记忆的候选数量、命中率和缓存热度可能不同，不能混在一组数据中下结论。因此本次分成两个等规模场景：

| 场景 | 可见记忆 | 另一作用域 |
| --- | --- | --- |
| 仓库专属记忆 | 当前仓库 `REPOSITORY:<id>` 中 300 条 | `GLOBAL` 中为 0 条 |
| 通用记忆 | `GLOBAL` 中临时构造的 300 条 | 当前仓库中为 0 条 |

临时全局记忆仅用于测试，结束后已从 MySQL、Qdrant 与 Redis 清理。两组使用相同的查询语义和候选规模，目的是比较检索后端，不是比较某类记忆天然更快。

## 结果

### 仓库专属记忆：300 条候选

| 路径 | 平均耗时 | P50 | P95 | 相对 Qdrant |
| --- | ---: | ---: | ---: | --- |
| Qdrant | **18.06 ms** | 17.68 ms | 20.94 ms | 基准 |
| Redis 三级缓存 | 64.68 ms | 62.01 ms | 83.17 ms | Qdrant 快 3.58 倍 |
| MySQL 无缓存 | 232.22 ms | 231.70 ms | 241.11 ms | Qdrant 快 12.86 倍 |

### 通用记忆：300 条候选

| 路径 | 平均耗时 | P50 | P95 | 相对 Qdrant |
| --- | ---: | ---: | ---: | --- |
| Qdrant | **14.84 ms** | 14.74 ms | 16.14 ms | 基准 |
| Redis 三级缓存 | 61.97 ms | 60.63 ms | 67.97 ms | Qdrant 快 4.18 倍 |
| MySQL 无缓存 | 228.83 ms | 228.92 ms | 236.09 ms | Qdrant 快 15.42 倍 |

### 耗时降幅

降幅按 `(对照耗时 - Qdrant 耗时) / 对照耗时` 计算。

| 场景 | 相比 MySQL 平均耗时降低 | 相比 Redis 平均耗时降低 | 相比 MySQL P95 降低 |
| --- | ---: | ---: | ---: |
| 仓库专属记忆 | 92.22% | 72.08% | 91.32% |
| 通用记忆 | 93.51% | 76.05% | 93.16% |

对外表述可使用“在 300 条候选、预热后串行检索实验中，Qdrant 相比 MySQL 直读平均耗时降低约 92%–94%”。这些数据不代表修复成功率或包含 Embedding 的端到端耗时。

## 结论与边界

Qdrant 的优势来自把 Top-K 相似度检索下推到向量索引；Redis 三级缓存虽然免除了 MySQL 往返，但仍要批量传输、反序列化并由 Java 对全部候选向量计算余弦相似度。候选量继续增长时，两者差距预计会扩大。

这不是生产压测：它没有覆盖并发请求、缓存冷启动、Embedding 网络抖动、混合作用域（全局加仓库）和大于 300 条候选的 P99 延迟。后续应补充这些场景，并分别观察全局热记忆与单仓库长尾记忆的命中率。

## 基准入口

开发环境提供受 Worker Token 保护的 `POST /internal/memory-benchmark/search`，由 `MemoryRetrievalBenchmarkController` 调用预计算 Embedding 的检索路径。该入口受 `MEMORY_RETRIEVAL_BENCHMARK_ENABLED` 控制，默认关闭，测试结束后远端已恢复为关闭状态。

## 召回质量测试：基于真实经验的小规模测试

截至历史迁移记录，已导入 10 条来自已验证成功案例的旧记忆。300 条候选是压测用扩展数据，不能计入真实经验数量。10 条记录也不一定对应 10 种独立技巧：旧数据同时支持 recipe、episode、semantic insight，应按来源与内容去重后再确定独立经验数量。

2026-09-30 核对时远端 SSH 超时，尚未确认数据库当前的真实记录数、有效状态和向量版本。因此 10 条是已知历史迁移数量，不是本次实时盘点结果，也没有新的召回质量得分。

建议先做以下测试，不需要为了凑规模扩写记忆：

1. 盘点这 10 条记录的来源、独立技巧、适用条件、状态和当前向量版本，去除重复与压测数据。相似记录作为同一个经验组标注。
2. 每个独立经验组准备 3 条正例查询：原始公开 Issue 描述、独立改写的问题描述、不同具体输入但适用同一技巧的问题。查询不复制经验的修复策略，也不包含最终 patch。原始 Issue 的命中只能说明来源问题可检索，单独统计。
3. 每组准备 2 条负例：关键词相似但契约不同的问题、缺少关键适用条件的问题。若有 10 个独立组，即约 30 条正例和 20 条负例；去重后按实际组数缩减。
4. 人工给每个查询标注适用 memoryId、经验组及不适用原因；允许一个问题对应多条适用经验。优先用其他真实公开 Issue，人工构造的查询单独报告。
5. 固定同一版记忆、Embedding 和检索配置，记录 Top-1、Top-3 的 Recall、首条适用经验排名 MRR、负例被最终注入的比例。召回候选与最终采用的经验分别记录。Top-5 作为补充，避免小候选集掩盖排序问题。
6. 验证仓库隔离与版本过滤：全局经验可见、当前仓库经验可见、其他仓库专属经验不可见、旧版本结果被剔除。此类正确性用例与语义召回得分分开报告。

历史导入经验存储在 `HISTORICAL_SWE_BENCH` 作用域，当前 `MemoryService` 不对 SWE-bench 任务开放该作用域。离线质量测试需显式选择它，不能直接用 SWE-bench 任务入口测出空结果后认定检索失败。测试不改变正常任务的作用域规则。

调参和最终检查按经验组划分，例如 6 组用于调参、4 组留出检查，同组查询不能分散到两边。候选记忆保持完整；留出的是查询及其标签。样本较少，应报告“命中数/查询数”和逐条失败原因，先验证基础检索与适用性判断，再扩大真实经验和查询规模。
